### Workspace inspection layer (planning — 2026-07-26)
Source: Notion page "Notas de Áudio 26/07" (2026-07-26) — surfaced indirectly: everything workspace//kit has built so far *writes* a workspace (`core/generator.js`, the HTML artifact, the planned CLI); the workspace-health-check, Markdown Orchestrator, cross-tool session log, document ingestion queue, and git file-state tracking ideas below all need the opposite — a shared way to *read* an existing workspace. Foundational, cross-cutting: a read-side counterpart to `core/generator.js` (e.g. `core/inspect.js`) that opens an existing workspace and returns an addressable index — which files exist, per-file size/line/character/estimated-token counts, individual instructions parsed out of the agent-layer files, and the cross-reference graph between files (the "RAG by Markdown" edges already described in CONTEXT.md).
- [ ] Confirm this as a distinct foundational piece (own spec + issue) rather than letting several feature specs each grow their own workspace parser
- [ ] Consumers to keep in view while scoping: workspace health check, Markdown Orchestrator, cross-tool session log, document ingestion queue, git file-state tracking, and the Local Web App's "open an existing workspace" P0 bullet above
- [ ] Surface reality: reading a folder needs a local process, so this is CLI/Web-App-only by the 2026-07-21 multi-surface policy — the standalone HTML artifact can't participate (it can only inspect content the user pastes/uploads into it)
- [ ] Decide where estimated token counting comes from (heuristic chars/4, a real tokenizer dependency, or model-specific) — bears on the "zero dependencies, no build step" convention `core/generator.js` currently holds

### Workspace health check — "system doctor" (planning — ingested from voice note, 2026-07-26)
Source: Notion page "Notas de Áudio 26/07" (2026-07-26). Workspace//kit should be able to evaluate the health of an existing workspace — its instructions, its history, and its file sizes — and give improvement suggestions, like a doctor for the workspace. Core problem: oversized instruction files (CLAUDE.md, AGENTS.md, the human layer) silently eat the context window and make the workspace *less* useful to any agent, and nothing today tells the user that's happening. Builds on the Workspace inspection layer above.
- [ ] Define the health metrics: number of instructions, per-file size, character count, estimated tokens consumed per file, total always-loaded context budget, history/log growth
- [ ] Define thresholds and a report format (per-file status + overall verdict) — reuse the ~300-line "always-loaded file" figure already recorded in docs/specs/context-manager-conventions.md as a starting point rather than inventing a second, conflicting number
- [ ] Define the improvement suggestions the doctor gives (split a file, move prose to an on-demand file, rotate decision-log entries, prune stale instructions, fix a broken cross-reference)
- [ ] Reconcile with docs/specs/context-manager-conventions.md → [#34](https://github.com/atempel/workspace-kit/issues/34): that spec is a manually-followed numeric policy covering CONTEXT.md/DECISIONS.md only, with automation explicitly a Non-Goal for v1. The doctor is measurement + suggestion across every file in a workspace — open question: does the doctor eventually absorb #34's product-facing half, leaving #34 as a repo-own-docs process only?
- [ ] Likely the CLI's natural second command (`workspace-kit doctor`) — needs no UI to be useful, worth building right after the CLI's generate flow works

### Git as the integration layer (planning — ingested from voice note, 2026-07-26)
Source: Notion page "Notas de Áudio 26/07" (2026-07-26). Git becomes the "glue" of workspace//kit, integrated in a user-friendly way: workspace//kit tracks file states and routes edits (needed by the Markdown Orchestrator) through git flows. Distinct from the amended `## Next` git bullet above, which is about *generated instructions* teaching an agent to use git — this is about workspace//kit itself operating git. CLI/Web-App-only by construction.
- [x] ~~Resolved 2026-07-26: does workspace//kit call an AI model itself?~~ — No. Workspace//kit stays model-agnostic. Keeps this consistent with the model-agnostic principle and the no-API-key constraint in CONTEXT.md.

- [x] ~~Surface split to clarify~~ — resolved 2026-07-21, per the multi-surface policy (DECISIONS.md): generating the Dockerfile/docker-compose *content* is just more generated text, so it's available from the standalone HTML too (same pattern as CLAUDE.md/AGENTS.md/.gitignore); actually spinning the container up in "a few steps" (running `docker build`/`docker compose up`) needs a local process, so that part is CLI/Web-App-only

### Shared instruction library across projects (planning — ingested from voice note, 2026-07-26)
Source: Notion page "Notas de Áudio 26/07" (2026-07-26). The owner works across multiple projects that need isolated contexts, but many instructions repeat across all of them (how to use Git/GitHub, general best practices). There's value in a single source of truth for those shared instructions, so projects become more homogeneous/consistent instead of each drifting its own copy. Deliberately sequenced after the Templates MVP — this overlaps Templates enough to risk being designed twice.
- [ ] Decide the relationship to Templates (#32): a template is reusable scaffolding applied *once* at creation; a shared instruction library is a *live* canonical source many existing workspaces keep referencing. Same content, opposite lifecycle — docs/specs/templates-feature.md currently lists "no live link between a template and workspaces generated from it" as an explicit Non-Goal, which this idea directly contradicts
- [ ] Decide the mechanism: physically copied into each workspace (duplication, drifts), referenced by path/import (breaks portability and the self-contained-workspace assumption), or synced/propagated on demand (needs update detection and conflict handling)
- [ ] Where the canonical library lives (a per-user global folder? its own git repo? — the latter converges with the enterprise/guardian idea in the Git section above)
- [ ] Interaction with the Markdown Orchestrator's on/off toggles: can a project disable an instruction that comes from the shared library, and does that survive a later sync?
