2026-07-29 Issue tracker pruned to the spec convention; spec→issue sync keyed instead of title-matched DECISIONS.md
  • Decision: the GitHub issue tracker is brought back to this repo's stated convention — one curated parent issue per spec, with its Must-Have (P0) requirements as linked sub-issues — by closing everything that predates or duplicates it. 78 issues closed in one pass, 168 open → 90: the 41 raw TASKS.md-bullet issues from the 2026-07-26 automation flood (#36–#76), 30 auto-titled twins of the hand-curated sub-issues #82–#111, 5 legacy issues whose work is provably done (#3, #10, #11, #18, #19), and 2 duplicates created the same day by the rename (#166, #168). Every closure carries a comment naming the canonical issue or the commit that completed it — nothing is closed silently.
  • Reason: the tracker had drifted into three overlapping layers (pre-spec bullets, curated sub-issues, and auto-generated twins of those same sub-issues), so it no longer answered "what is actually left to do." The owner asked for a clean slate before changing the project's direction.
  • Decision: the Sync specs to Issues workflow matches issues by a stable sync key (<!-- sync-key: <spec>#p0-<n> --> in the issue body), not by exact title. Retired (struck-through) requirement bullets are skipped. Titles are never rewritten unless explicitly asked for.
  • Reason: title matching failed twice for real on this date. The kit rename reworded a P0 bullet and duplicated #126 as #166; a bullet that had just been struck through and retired became #168, titled with the literal ~~...~~ markup. Both failures are structural, not accidents — any future rewording would have repeated them. Ordinals span all bullets including retired ones, so retiring a requirement does not renumber the rest and invalidate their keys.
  • Also decided: when adopting pre-key issues, the parent's existing linked sub-issue at the same ordinal wins over an exact-title match. This is what keeps the hand-curated #82–#111 canonical rather than letting the auto-titled twins take their place. Known limitation, documented in the script: keys are positional, so reordering P0 bullets within a spec will mismatch issues — adding and retiring are safe.
  • Alternatives considered: requiring an explicit stable id in every spec bullet (e.g. - (P0-3) …) — discarded as noise in a document meant to be read by humans; hashing the bullet text as the key — discarded, it is the text that changes, which is the whole problem.
  • Implementation note: the logic moved out of an inline heredoc in the workflow YAML into .github/scripts/sync_specs_to_issues.py, which takes --dry-run. Every number above was verified against the live repo with that flag before anything was written.
2026-07-29 `core/inspect.js` implemented; the inspection layer's open questions closed DECISIONS.md
  • Decision: the workspace inspection layer (docs/specs/workspace-inspection-layer.md → #77) is implemented as core/inspect.js, the read-side counterpart to core/generator.js — same conventions (plain Node-compatible JS, zero runtime dependencies, no build step), verified by npm run test:inspect, whose 18 cases map 1:1 onto the spec's P0 acceptance criteria so a failure names the requirement it breaks.
  • Decision (was an Open Question): estimated token counts use the characters ÷ 4 heuristic, swappable through an estimateTokens option. A real tokenizer would mean a runtime dependency, which is exactly the convention this module exists to mirror; and #78's own P0 already assumed chars ÷ 4, so picking anything else would have split the two. Consumers must present the number as an estimate (#169 P0 requires it).
  • Decision (was an Open Question): one instruction unit = one markdown heading section, plus a preamble unit for content before the first heading — a generated CLAUDE.md opens with a bare @AGENTS.md import, which is itself an instruction and would otherwise be invisible. IDs are path#heading-slug, deterministic from content, deduplicated with a numeric suffix. The Markdown Orchestrator still owns the definitive unit; when it lands, parseInstructions is the single place that changes.
  • Decision (was an Open Question): Node-only export. No window.* global like core/generator.js's UMD-lite wrapper, since reading an arbitrary folder needs fs and no browser surface consumes this.
  • Decision (not in the spec, forced by reality): the scan honours the workspace's own .gitignore and skips nested git repositories. Inspecting this repo without either produced 693 files, 14.6 MB and 7.7 seconds — it was indexing .claude_global/ and a .claude/worktrees/ checkout of the repo itself, and 9 of the 10 "broken cross-references" it reported came from third-party plugin content. With both rules: 72 files, 320 ms, zero broken references. Health-check verdicts computed over the first set would have been meaningless, so this is a correctness matter, not an optimisation. Opt out with respectGitignore: false. A directory carrying its own .git is treated as a separate project rather than part of this workspace.
  • Decision: markdown links inside inline code do not create graph edges (prose mentions still do). The spec's own line 43 writes "standard [text](path) links" as a syntax example, and the first implementation dutifully recorded an edge to a file named path — a fabricated edge, which the P0 acceptance criterion explicitly forbids. Mentions are deliberately exempt: they only ever resolve against files that exist, so they cannot invent a target, and this repo's prose refers to real files in backticks constantly.
  • Consequence worth keeping in view: the fixture workspace the tests run against is generated by core/generator.js at test time rather than committed as static files, so the read side is always checked against what the write side currently produces. A generation change the inspector cannot read fails the suite instead of reaching a consumer.
  • Alternatives considered: committing a static fixture workspace — discarded, it would drift from the generator exactly like the HTML artifact's inline copy already does; reporting unresolved edges only when the target looks like a filename — discarded as a second mechanism for a bug the inline-code rule already fixes at its cause.

2026-07-29 The local server is zero-dependency and read-only DECISIONS.md
  • Decision: core/server.js — the local HTTP surface the Web App dashboard consumes — uses Node's own http and takes no dependencies. The React/Tailwind/shadcn build step decided 2026-07-28 is scoped to the front end that consumes this server, not to the server itself. 2026-07-29 Worktrees: convention by default, override always available DECISIONS.md
  • Decision: worktree placement and naming follow a convention the user never has to think about — <workspace>/.worktrees/<name>, on a branch of the same name — while --path and --branch let the user override either. This answers the spec's "auto-place vs. prompt every time" question with both, ordered: convention first, control on request. Removal keeps the branch; deleting a branch is a separate, more destructive decision than removing a directory.
  • Reason: the owner's call, and the two options were never really exclusive — prompting every time taxes the common case (spin up an isolated copy for another agent), while a rigid convention blocks the uncommon one. A default that is right most of the time plus an explicit escape hatch costs one extra flag and no ambiguity.
  • Why inside the workspace, not a sibling folder (the spec's own example was ../workspace-name-agent2/): a workspace stays one movable, self-contained directory, and every other module here already refuses to reason about paths outside the workspace root — core/server.js rejects them outright. Nesting is only safe because the read side already accounts for it: core/inspect.js skips nested git repositories, so a worktree's files never get folded into the parent's index or health check. A sibling would make a workspace's own worktrees the one thing living outside itself.
  • Consequence handled here: any worktree placed inside the repository — by convention or by the user's --path — would otherwise show up in the parent's own status as a stray directory. Creating one adds the ignore rule, once, under a single heading. This is the same defect workspace-kit status found in this repo (.claude/worktrees/ untracked), fixed at the source rather than by hand.
  • Alternatives considered: sanitising invalid worktree names into valid ones — discarded, quietly rewriting a name the user chose creates the worktree somewhere other than where they asked, which is worse than refusing; deleting the branch on removal — discarded, it can hold the only copy of committed work.
  • Applies to: docs/specs/git-integration-layer.md (#79), core/git.js, bin/workspace-kit.js.
2026-07-29 Templates and the shared instruction library do not conflict: generation ends where management begins DECISIONS.md
  • Decision: the shared instruction library (TASKS.md) is not blocked by the Templates spec's "no live link between a template and workspaces generated from it" Non-Goal. The two operate in different phases and the Non-Goal was read too broadly.
  • Reason: the owner's correction, and it is right. A template is a generation-time artifact: a one-shot source that lays a workspace's foundation and is done. From the moment that folder exists it is a living workspace, and everything after that — including whether it keeps shared instructions in sync with a central library — is management, a different phase with a different owner. The Non-Goal constrains templates specifically: it rules out versioning templates and diffing template updates against already-generated workspaces. A library→workspace link established after generation is a different relationship between different objects, and nothing in that Non-Goal reaches it.
  • Wider point worth keeping: generation and management are separate phases, and this codebase already splits exactly that way — core/generator.js writes, core/inspect.js/doctor.js/git.js manage. Blockers should be checked against which phase they actually constrain before being treated as binding.
  • Correcting the record: the 2026-07-29 report and TASKS.md both listed this as blocked pending reconciliation. It was not blocked; the analysis conflated "reusable source of text" with "template". The shared instruction library now needs a spec, not a decision.
  • Applies to: docs/specs/templates-feature.md (#32), TASKS.md.
