## 2026-07-29 — Git layer: the unblocked half built, the PR/worktree half deliberately not
- **Decision:** `core/git.js` implements the part of docs/specs/git-integration-layer.md (→ #79) that no open question gates — file-state tracking, the safe-edit substrate, the plain-language change summary, and the templated commit message — plus a `workspace-kit status` command. The **PR flow and worktree management are not built**, because each is gated on a "(Product — Alexandre)" question in the spec: hosting-provider scope (GitHub-only via `gh` vs. provider-agnostic) and worktree placement/naming (auto-placed by convention vs. prompted). Both answers determine the implementation, so building ahead of them means throwing a version away.
- **Decision:** when a file is staged *and* has further unstaged edits, it reports as `modified-unstaged`. The unrecorded change is the one a caller about to overwrite the file needs to know about; reporting `staged` there would make the safe-edit check quietly wrong in exactly the case it exists for.
- **Decision:** git is driven by `execFileSync` with explicit argument arrays, never a shell string. A test writes a file named `a file; echo pwned > owned.txt.md` and asserts it is reported literally and nothing executes.
- **Reason for the guardrail tests:** #79's model-agnostic requirement and its "the HTML artifact is unchanged" requirement are both product rules that are easy to violate later by accident. Each is now a test — one asserting `core/git.js` contains no outbound call and depends only on `child_process`/`path`, another asserting `src/workspace-kit.html` never references this feature.

## 2026-07-29 — The local server is zero-dependency and read-only
- **Decision:** `core/server.js` — the local HTTP surface the Web App dashboard consumes — uses Node's own `http` and takes **no dependencies**. The React/Tailwind/shadcn build step decided 2026-07-28 is scoped to the *front end that consumes* this server, not to the server itself. Putting a framework here would place a dependency underneath every `core/` consumer, including the CLI.
- **Decision:** it owns **no domain logic**. Every endpoint is a thin envelope over `inspect`/`doctor`/`git`. That is what makes the CLI and the Web App produce identical answers by construction rather than by discipline — the property that motivated choosing a local server over the browser File System Access API in the first place.
- **Decision:** the server is **read-only** — every non-GET method is refused, and it must not grow write endpoints ahead of #79's blocked commit/PR/worktree questions. `/api/dashboard` reports `capabilities: {commit: false, pullRequest: false, worktrees: false}` so the UI renders those controls as unavailable instead of drawing live-looking buttons over nothing.
- **Decision:** `/api/dashboard` returns all five sections from **one scan**. Letting the dashboard issue four requests would let its sections disagree with each other mid-refresh, which is a worse failure than a slightly larger payload.
- **Security posture:** binds to `127.0.0.1` only and refuses any workspace path resolving outside the root it was started with. A browser page on another origin can still reach localhost, so "read any path on disk" would be a real hole, not a theoretical one.

## 2026-07-29 — Git layer scoped to local git; push and PRs deferred as their own step
- **Decision:** the git integration layer (`docs/specs/git-integration-layer.md` → #79) is **local-only** for now. It tracks state, drives commits and manages worktrees against the local repository, and contacts no remote — nothing is pushed, no PR is opened, no hosting provider is contacted. This closes the spec's "hosting-provider scope for the PR flow" open question by removing it from scope rather than answering it: the question stands, but it is not this step's to answer.
- **Reason:** the owner's call. Remote operations drag in authentication and a hosting-provider surface whose security deserves a deliberate pass of its own, and none of the local value — safe edits, parallel agents, plain-language commits — depends on them. Shipping the local half now is strictly better than a half-built remote half alongside it.
- **Alternatives considered:** building a GitHub-only PR flow via `gh` now and generalising later — discarded, it front-loads the provider decision the owner explicitly wants to take later, and a `gh` dependency is hard to retract once flows depend on it; a provider-agnostic abstraction over push/PR with no provider implemented — discarded as machinery with nothing behind it.
- **Enforced, not just documented:** `npm run test:git` asserts `core/git.js` contains no push/fetch/clone/pull and no `gh pr` call, so "local only" fails the build if it stops being true.
- **Applies to:** `docs/specs/git-integration-layer.md` (#79), `core/git.js`, `bin/workspace-kit.js`.

## 2026-07-29 — Worktrees: convention by default, override always available
- **Decision:** worktree placement and naming follow a convention the user never has to think about — `<workspace>/.worktrees/<name>`, on a branch of the same name — while `--path` and `--branch` let the user override either. This answers the spec's "auto-place vs. prompt every time" question with *both*, ordered: convention first, control on request. Removal keeps the branch; deleting a branch is a separate, more destructive decision than removing a directory.
- **Reason:** the owner's call, and the two options were never really exclusive — prompting every time taxes the common case (spin up an isolated copy for another agent), while a rigid convention blocks the uncommon one. A default that is right most of the time plus an explicit escape hatch costs one extra flag and no ambiguity.
- **Why inside the workspace, not a sibling folder** (the spec's own example was `../workspace-name-agent2/`): a workspace stays one movable, self-contained directory, and every other module here already refuses to reason about paths outside the workspace root — `core/server.js` rejects them outright. Nesting is only safe because the read side already accounts for it: `core/inspect.js` skips nested git repositories, so a worktree's files never get folded into the parent's index or health check. A sibling would make a workspace's own worktrees the one thing living outside itself.
- **Consequence handled here:** any worktree placed inside the repository — by convention *or* by the user's `--path` — would otherwise show up in the parent's own status as a stray directory. Creating one adds the ignore rule, once, under a single heading. This is the same defect `workspace-kit status` found in this repo (`.claude/worktrees/` untracked), fixed at the source rather than by hand.
- **Alternatives considered:** sanitising invalid worktree names into valid ones — discarded, quietly rewriting a name the user chose creates the worktree somewhere other than where they asked, which is worse than refusing; deleting the branch on removal — discarded, it can hold the only copy of committed work.
- **Applies to:** `docs/specs/git-integration-layer.md` (#79), `core/git.js`, `bin/workspace-kit.js`.

## 2026-07-29 — Templates and the shared instruction library do not conflict: generation ends where management begins
- **Decision:** the shared instruction library (TASKS.md) is **not** blocked by the Templates spec's "no live link between a template and workspaces generated from it" Non-Goal. The two operate in different phases and the Non-Goal was read too broadly.
- **Reason:** the owner's correction, and it is right. A template is a **generation-time** artifact: a one-shot source that lays a workspace's foundation and is done. From the moment that folder exists it is a living workspace, and everything after that — including whether it keeps shared instructions in sync with a central library — is **management**, a different phase with a different owner. The Non-Goal constrains *templates* specifically: it rules out versioning templates and diffing template updates against already-generated workspaces. A library→workspace link established after generation is a different relationship between different objects, and nothing in that Non-Goal reaches it.
- **Wider point worth keeping:** generation and management are separate phases, and this codebase already splits exactly that way — `core/generator.js` writes, `core/inspect.js`/`doctor.js`/`git.js` manage. Blockers should be checked against which phase they actually constrain before being treated as binding.
- **Correcting the record:** the 2026-07-29 report and TASKS.md both listed this as blocked pending reconciliation. It was not blocked; the analysis conflated "reusable source of text" with "template". The shared instruction library now needs a spec, not a decision.
- **Applies to:** `docs/specs/templates-feature.md` (#32), TASKS.md.

## 2026-07-29 — Dashboard front end: Vite, vendored primitives, and a read-only v1
- **Decision:** the Local Web App dashboard (`docs/specs/web-app-dashboard.md` → #169) is built with **Vite + React 19 + Tailwind v4**, living in `web/` with **its own `package.json`**. Root `npm test` stays the zero-dependency core suite; the dashboard's tests run via `npm run test:web`.
- **Reason:** the React/Tailwind/shadcn stack was already decided 2026-07-28; this fills in the parts that decision left open. A separate package is what keeps that decision's scope honest — `core/` and the CLI still install nothing, so the build step genuinely applies only to the surface that consumes them, rather than leaking underneath everything.
- **shadcn/ui components are vendored, not generated.** The dashboard needs a card, a badge, a table, a button and a status marker. Running the shadcn CLI would pull Radix's focus-management and portal machinery behind five styled elements that never open, trap focus or portal anything. `web/src/components/ui.jsx` implements them directly against the prototype's tokens. Revisit if the UI grows controls that genuinely need Radix's behaviour (dialogs, popovers, comboboxes) — this is a "not yet", not a "never".
- **The `Status` component is load-bearing, not cosmetic.** The spec makes "colour + icon + text, never colour alone" a P0 accessibility criterion across all five sections. Centralising it in one component is what makes that hold everywhere, and a test asserts every rendered status carries both an icon and a text label.
- **v1 renders; it does not execute.** Every `capabilities` flag is false and the UI draws those actions as unavailable *with the reason*. Two independent reasons, worth keeping separate: the local server is read-only and rejects non-GET, so any write belongs to the CLI; and pull requests are out of scope entirely while the git layer stays local-only (see the 2026-07-29 entry above). The spec named a CLI-first v1 as "a legitimate smaller v1" — this is that.
- **Alternatives considered:** putting the dashboard's dependencies in the root `package.json` — discarded, it would make every `core/` consumer install React to run a CLI; adding write endpoints to `core/server.js` so the UI could commit — discarded, it breaks the read-only guarantee a test currently enforces, and the owner has not asked for UI-driven git.
- **Applies to:** `docs/specs/web-app-dashboard.md` (#169), `web/`, `core/server.js`.

## 2026-07-29 — Everything lands on one long-lived branch, not on main
- **Decision:** all work now goes to the `dashboard` branch and stays there. No pull requests to `main`, and no per-task branches. `main` stays exactly where it is (`97a943d`) until the dashboard is finished and tested, at which point the branch is integrated in one piece. Cowork's report layer moved onto this branch too, so Claude Code and Cowork build in the same place rather than in parallel copies.
- **Reason:** the owner's call. The repository is public, so `main` is what anyone arriving at the project reads; a half-built feature landing there in pieces misrepresents the project's state. Consolidating also ends the per-task worktree sprawl of 2026-07-29, where finished work sat in six separate branches with no single place to see it whole.
- **Consequence:** `reports/` now holds both kinds of file — generated by `npm run report` and hand-authored — with the boundary written down in `AGENTS.md` and `reports/README.md`. Markdown stays the source of truth for documentation; `reports/` is its human-readable rendering, never a replacement for it.

## 2026-07-30 — Two dashboards became one: `web/` kept, `app/`'s Playwright harness kept with it
- **Decision:** the parallel implementation in `app/` (branch `worktree-dashboard`) is retired and `web/` is the dashboard. Its browser-level verification harness is not retired — it was ported into `web/` as `check-ui.mjs` and now runs as `npm run test:ui`. The two front ends had been built simultaneously by different sessions against the same spec; the owner chose `web/` after seeing both running side by side.
- **Reason:** `web/` covers more of the spec's P0 surface today — safe-edit warning, worktree list, and blocked-action copy that names the *current* reasons — because it tracks the current `core/`. `app/` predates the 2026-07-29 local-git-only and worktree-convention decisions and still told the user those questions were open. `web/` also carries no runtime dependency beyond React, where `app/` pulled lucide-react, clsx, cva and tailwind-merge; that matches the dependency discipline the rest of the project holds to. Closing the gap on `app/` was strictly more work than closing it on `web/`.
- **But the method question went the other way, and that is the durable part.** Running both exposed that `web/` was broken in a browser — it rendered `health.method`, an object, as a React child, so the page mounted blank. Its 12 server-render checks had been green throughout, because they render the five *sections* and the crash was in the *shell*. A build passing is not evidence a UI works; only a browser is. So the harness is kept and the two suites are treated as complementary rather than redundant: `check-render.cjs` enforces the data-boundary rules cheaply and without a browser, `check-ui.mjs` proves the built app boots, navigates and shows the API's own numbers.
- **Consequence:** UI markup now carries stable `data-*` hooks (`data-nav`, `data-file`, `data-suggestion`, `data-queue-status`, `data-session`, `data-capability`, `data-theme-toggle`) plus `aria-current` on the active nav item — the harness addresses those rather than CSS classes or visible text, so restyling cannot silently break the tests. The always-loaded budget gained a real `role="meter"` with `aria-valuenow`, which `app/` had and `web/` did not; that is an accessibility gain, not just a test hook. `web/` moved to ports 4330/4331: it and `app/` had used the same two ports with dev and preview swapped, so during the comparison each could answer for the other, and an orphaned preview server did exactly that. `strictPort` now makes a collision fail loudly.
- **Alternatives considered:** keeping `app/` and porting `web/`'s coverage into it — discarded, more work in the direction of the older `core/`; keeping both behind a flag — discarded, a second dashboard that nobody runs goes stale silently, which is the failure this entry exists to prevent; replacing `check-render.cjs` with the Playwright suite — discarded, the fast suite is what makes the "no hard-coded data, no threshold of its own" rules cheap enough to enforce on every change.
- **Applies to:** `web/`, `docs/specs/web-app-dashboard.md` (#169). Branch `worktree-dashboard` was deleted locally; `origin/worktree-dashboard` is deliberately left in place as the recoverable record of the discarded implementation.

## 2026-07-30 — `workspace-kit serve` serves the built dashboard itself; `--host` exists for containers
- **Decision:** `core/server.js` serves the compiled front end from `web/dist` at `/`, alongside the JSON at `/api/*`. Using the dashboard is now one command and one port — `npm --prefix web run build` once, then `workspace-kit serve .` — with Vite needed only when working on `web/` itself. `createServer(root, { ui: false })` keeps the pure JSON surface the dev proxy and the tests want.
- **Reason:** the owner asked when the app could be tested from Windows, and the answer exposed the real obstacle: this project develops inside a Docker container that published no ports, and requiring a Vite dev server meant two processes and two ports to expose rather than one. Beyond that, "install Node, install the front end's dependencies, run a bundler" is not a reasonable way to *use* a local tool — it is a way to develop it.
- **This is a deliberate, narrow exception to "core/inspect.js is the only module that touches the disk."** That rule exists so the workspace is read in exactly one place and the CLI and dashboard cannot disagree about what they saw; it still holds — nothing here reads the workspace. Serving bytes the build already produced is not domain logic. The alternative, injecting a file reader from `bin/` the way `core/git.js` takes its `io`, works for git's handful of calls and would be ceremony around an HTTP file server.
- **Security:** the path-escape check that guards the workspace root now guards the asset directory too, and a test asserts `../secret`, `/../../etc/passwd`, percent-encoded traversal and `assets/../../` all fail to read outside it. Non-GET is still refused at `/` as well as at `/api/*`, also tested. The default bind is unchanged at 127.0.0.1; `--host` widens it, prints a warning naming what that exposes, and `docker-compose.yml` publishes the container's ports to the host's loopback only (`127.0.0.1:4319:4319`) rather than to every interface.
- **Alternatives considered:** leaving the dashboard on Vite and telling the user to publish two ports — discarded, it makes a bundler part of the runtime story for a tool that is otherwise a Node CLI; a separate static-server binary or dependency — discarded, `core/` stays zero-dependency and Node's `http` already had everything needed; serving the dashboard from a *different* port than the API — discarded, one origin means no proxy, no CORS, and one thing to expose.
- **Found while preparing the container recreate, and worth writing down:** the compose file persisted *less* than it looked like it did. `/workspace` and `/root/.claude` are bind mounts, so code, git, worktrees, Claude memories and session transcripts were always safe — but Claude Code's account lives in `~/.claude.json`, **outside** `~/.claude`, and the `gh` token lives in `~/.config/gh`. Both were container-only, so any `docker compose up -d` would have silently logged the account out and broken `git push` (the global gitconfig routes credentials through `gh auth git-credential`). Both are now persisted: `.claude.json` by bind, `gh` by named volume. Named volumes also hold `~/.npm` and `~/.cache`, mostly so the ~650 MB Playwright browser download that `npm run test:ui` needs survives a recreate. The bind for `.claude.json` requires the host file to exist first — Docker replaces a missing bind-mounted *file* with a directory, which would break startup rather than degrade it.
- **Applies to:** `core/server.js`, `bin/workspace-kit.js` (`--host`), `docker-compose.yml`, `docs/specs/web-app-dashboard.md` (#169), `docs/specs/local-web-app.md` (#29).

## 2026-08-01 — Dashboard view state persists in the browser, not on the server; the P1 shell affordances built
- **Decision:** suggestion dismissals, the recent-workspace list and theme all persist in `localStorage` (`web/src/lib/prefs.js`), keyed by workspace root where they are workspace-specific. This closes the Open Question docs/specs/web-app-dashboard.md had carried since 2026-07-29 — "whether these persist, and if so where (local config file vs. browser storage)".
- **Reason:** `core/server.js` is read-only by construction and refuses every non-GET method, which is the guarantee that lets the CLI and the dashboard provably share one analysis. Persisting any of this server-side means opening a write endpoint, and trading that guarantee for a checkbox is a bad exchange. The deeper reason is that none of the three is a fact about the workspace — they are facts about how one person is looking at it, and workspace facts belong in the workspace's files where the CLI can read them too.
- **Cost, accepted and named in the code:** preferences do not follow the user to another browser, and clearing site data resets them. Nothing is destroyed when that happens — a dismissed suggestion reappears, which is the safe direction for the failure to fall.
- **Dismissal is a view filter and nothing more.** It does not touch the verdict, the finding count, or what `workspace-kit doctor` reports; the screen states this rather than leaving it to be inferred, and both test suites assert it. A dismissal that quieted the verdict would make the two surfaces disagree about the same workspace, which is precisely what this data layer exists to prevent.
- **The workspace switcher can remember and cannot open, and says so.** The server binds one root for its lifetime, so the switcher lists where the user has been and offers the `workspace-kit serve <path>` command to get back. Drawing a live-looking switcher over a server that cannot rebind would be the same dishonesty the Source control section's disabled buttons exist to avoid.
- **The command palette is navigation-only, on the same principle:** every *action* in this dashboard is currently unavailable-with-a-reason, and a palette offering "Commit changes" only to explain it cannot would be worse than one that never offers it. Sections and files, nothing else. The shape allows actions later.
- **Worktree overlap is reported, not judged** (`worktreeConflicts()` in `core/git.js`, #79's P1): which files two worktrees hold uncommitted changes to at the same time. "Uncommitted" is the scope on purpose — once work is committed it belongs to a branch, and whether two branches conflict is a merge question, not a worktree one. The main working copy counts as a holder like any other; being "the real one" does not exempt it.
- **Alternatives considered:** a local config file under the workspace (e.g. `.workspace-kit/ui.json`) — discarded, it needs a write path and would put per-viewer preferences into a folder that is committed and shared; ids emitted by `core/doctor.js` to key dismissals by — discarded, an id would be a UI concern leaking into the analysis layer and the CLI has no use for one, so the key is derived in the UI from kind + file + message, which also makes a *reworded* finding reappear rather than stay dismissed under an old decision; pulling `cmdk` for the palette — discarded, `web/` vendors its primitives (2026-07-30) and the whole behaviour is a filtered list with four keys bound to it.
- **Also in this pass:** Chromium's shared libraries added to the `Dockerfile`. The browser binary stays on the `wskit_cache` volume (~650 MB, versioned by the playwright package), but the apt-owned libraries it links against were hand-installed into the old container and a recreate dropped them — the same class of loss as the `gh` binary on 2026-07-30, and the same fix. Takes effect on the next `docker compose up --build`.
- **Applies to:** `web/src/lib/prefs.js`, `web/src/components/CommandPalette.jsx`, `web/src/components/Sidebar.jsx`, `web/src/sections/Health.jsx`, `web/src/sections/Overview.jsx`, `web/src/sections/SourceControl.jsx`, `core/git.js`, `core/server.js`, `Dockerfile`, `docs/specs/web-app-dashboard.md` (#169), `docs/specs/git-integration-layer.md` (#79).

## 2026-10-11 — `reports/` is local output, not versioned
- **Decision:** `reports/` is gitignored and removed from the index (files kept on disk). Both kinds of content that lived there — the pages `npm run report` generates and the hand-authored one-offs — are now local to whoever produced them. Closes the TASKS.md open question "commit `reports/` or gitignore it".
- **Reason:** the owner's call. The generated pages are a pure function of the Markdown sources, so versioning them only doubled every docs diff and invited drift between the `.md` and its rendering; the one-offs were read on the machine that wrote them. Markdown remains the source of truth either way.
- **Cost, accepted:** the HTML is no longer browsable straight from GitHub, and a hand-authored report that should outlive the machine has to be promoted into `docs/` as Markdown. Links from versioned docs into `reports/` were removed for the same reason — a link to an ignored path is a link that breaks on every fresh clone.
- **Alternatives considered:** ignoring only the generated pages and versioning the one-offs — discarded as the split the owner did not ask for, and one that keeps the folder's mixed nature alive.

## 2026-10-11 — Templates technical design: a manifest-driven renderer that reuses the generator rather than forking it
- **Decision:** docs/specs/templates-technical-design.md (→ #22, PR #195) fixes the design before any code: a template is a folder plus a manifest, merge tags use a `%tag%` grammar with a `%%` escape and map onto the generator's existing fields, and a `renderTemplate` function reuses `core/generator.js` instead of duplicating it. Surfaces are sequenced core → CLI → Web App read-only → artifact last.
- **Reason:** the Templates feature (#32) touches four surfaces; deciding the manifest, tag grammar and storage/naming (#26) once, in the shared module, is what keeps them from each inventing their own. A forked renderer would recreate the drift the artifact's inline copy already has (see 2026-07-22).
- **Status:** a recommendation, not a settled design. Twelve questions remain open for the owner (tag marker, extending built-in kits, storage locations, write endpoints on the server, among others) and are tracked in TASKS.md, not here.
- **Alternatives considered:** a second generation path just for templates — discarded, it forks the logic; building the artifact side first — discarded, it is the one surface that cannot share the module without a build step.
- **Applies to:** `docs/specs/templates-technical-design.md` (#22), `docs/specs/templates-feature.md` (#32).

## 2026-10-11 — Generated workspaces carry the session log, the queue and rotation; git and visual are opt-in form options
- **Decision:** every generated workspace now includes `SESSIONS.md` (with one worked first entry), an empty `queue/` folder, and an "Every session" section in the agent layer covering the session-log append, the queue stub format and the ~15-entry DECISIONS.md rotation rule (PR #196, closing #110, #12, #14; the generated-text half of #120). Two new form options: "This folder will be a git repo" (default off) and "I'm a visual person". Both copies of the generation logic change identically; inputs gain `git` and `visual` booleans.
- **Decision:** with git **off**, `.gitignore` is **no longer generated**, and placeholders are `.keep` instead of `.gitkeep`. This follows #12 literally ("nothing about git") but changes the default output, since `.gitignore` was always emitted before. **Not settled:** it may conflict with the security & privacy pillar (a generated workspace could now commit local-only folders by accident) and has been flagged to the owner as an open question in TASKS.md.
- **Decision:** `queue/` ships empty, with the stub format documented in the agent layer rather than a `queue/README.md`, because `core/inspect.js` parses every `queue/*.md` as a stub. The first `SESSIONS.md` entry uses an ISO date so `inspect` parses it. The starter prompt is unchanged. The rotation rule is included unconditionally, with no opt-in.
- **Alternatives considered:** always generating `.gitignore` and hiding only the git prose — discarded as not "nothing about git", though it is the safer default for privacy and is the live alternative if the owner overrules; a `queue/README.md` — discarded, the inspector would read it as a stub.

## 2026-10-11 — `workspace-kit new`: the writer lives in `core/scaffold.js`, not in the generator or the inspector
- **Decision:** the CLI generator (docs/specs/cli-generator.md → #20, PR #197, closing #112–#116, #21) places `core/generator.js` output on disk through a new `core/scaffold.js`. `inspect.js` stays the only reader and read-only; `generator.js` stays fs-free because it also loads in a browser; scaffold never produces content, so no generation logic is forked. Verified by `core/check-new.js` (`npm run test:new`), including all 17 kits × EN/PT byte-compared against the generator.
- **Decision:** generator options map generically — if `core/generator.js` exports `OPTIONS` (`[{ key, type }]`), each becomes `--key-name`/`--no-key-name` with no CLI change; until then `--set k=v` (dotted for nesting) reaches any input key. Flags skip their prompt; `-y` never prompts and takes defaults, for CI.
- **Decision:** only the starter prompt goes to stdout; progress, prompts and the overwrite report go to stderr, so `workspace-kit new d > prompt.txt` works. `--git` is `git init` plus a first commit (`--no-commit` for init only); a failed commit is a warning; an existing repo is left untouched; git is driven by explicit argument arrays, as in `core/git.js`.
- **Decision:** a target is non-empty if it has any entry other than a bare `.git`, so `git init` then `new` works. `--force` overwrites only same-named files and lists them; paths escaping the target are refused. `--dry-run` (a P1) was pulled in since it cost a few lines. Default agents are `claude,agentsmd`, matching the form's pre-ticked boxes.
- **Alternatives considered:** letting the generator write files — discarded, it breaks the browser build; putting the writer in `inspect.js` — discarded, it ends the read-only guarantee.
- **Open:** where `OPTIONS` should come from, and npm/`npx` packaging, are left to the owner (TASKS.md).

## 2026-10-11 — First-run onboarding is a self-deleting `ONBOARDING.md`; recurring tasks live in `TASKS.md`
- **Decision:** the first-run mechanism (#9, PR #198, closing #7, #8, #9) is a separate `ONBOARDING.md` plus a two-line conditional "First session" pointer in the always-loaded agent file ("if `ONBOARDING.md` exists, follow it first; it is deleted when done"). The file guides filling PROJECT/CONTEXT/DECISIONS/TASKS, reviewing the created folders, proposing a first plan, and then appends to `SESSIONS.md` and deletes itself — the deletion is the once-only mechanism. The only permanent line is one bullet under "Every session": suggest organizational improvements and wait for approval, never move, rename or delete unprompted.
- **Reason:** the starter prompt is not a file, so it is lost across tools and sessions, while a file works in every agent tool. Cost in always-loaded files is about 3 lines (sample workspace: 53 lines across 2 files, 18% of the 300-line budget, doctor HEALTHY).
- **Decision:** recurring-task suggestions (#8) go in `TASKS.md` under "Recurring", three kit-specific bullets for each of the 17 kits (new `recurring` field in `KIT_CONFIG`, EN and PT), as plain bullets so they do not count as open tasks. They are ongoing by nature and the user edits them where tasks live. `ONBOARDING.md` is not listed in the generated README index, and has no opt-out checkbox.
- **Alternatives considered:** everything in the starter prompt — discarded, see above; the onboarding text in the permanent agent file — discarded, it would repeat in every conversation, which is exactly the problem #9 describes.
