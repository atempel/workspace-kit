## 2026-07-01 — Repository translated to English + bilingual generator planned
- **Decision:** the repository's own documentation (README, PROJECT, DECISIONS, CONTEXT, TASKS, AGENTS, CLAUDE, docs/PRD, research/) is now maintained in English only, replacing the Portuguese versions — no parallel bilingual docs. The generated artifact (`src/workspace-kit.html`) will get a PT/EN language selector covering both UI text and the physical folder names it generates (e.g. "pesquisa" → "research"), not just prose inside files.
- **Reason:** the project is moving toward a broader, GitHub-facing audience, and a single source of truth in English avoids double maintenance of the repo's own docs. For the generator's own output, translating only prose while keeping folder names fixed in Portuguese would leave a generated workspace inconsistent (English file content inside Portuguese-named folders), defeating the point of a language selector.
- **Alternatives considered:** keeping parallel bilingual repo docs (e.g. `README.md` + `README.pt-BR.md`) — discarded for ongoing double maintenance; translating only the generator's UI chrome while keeping folder names fixed in Portuguese — discarded for producing inconsistent generated output.
- **Supersedes:** the CONTEXT.md convention "interface and generated file texts in Portuguese (PT-BR)" recorded under v2 identity — see the updated CONTEXT.md convention.
- **Implemented:** the PT/EN selector was added to `src/workspace-kit.html` (2026-07-01), defaulting to English per the owner's call. It covers UI chrome, generated file templates, and generated folder names (e.g. "pesquisa" → "research"), driven by a `LANG` state and per-language `UI`/`TYPE_CONFIG` dictionaries — no `localStorage`, since the artifact also needs to run inside Claude.ai where that API is unavailable.

## 2026-07-01 — Project pillars: security & privacy, collaboration
- **Decision:** the project declares two explicit pillars, recorded in PROJECT.md: security & privacy, and collaboration.
- **Reason:** came out of a privacy audit of the repository (triggered by the owner's discomfort about making it public) and the resulting `.gitignore` discussion. Security & privacy: the repo and the generator's output must never expose secrets, personal data, or private discussion. Collaboration: the generated context layer exists so multiple people (and agents) can pick up a project without re-litigating past decisions, and local-only per-user state should be isolated rather than versioned.
- **How to apply:** future features (starting with the `.gitignore` generation task) should be evaluated against both pillars — e.g., what's heavy/sensitive stays local (privacy), and what helps a new collaborator or agent onboard faster stays documented and versioned (collaboration).

## 2026-07-02 — Generated `.gitignore` + 17 project types (11 → 17)
- **Decision:** `src/workspace-kit.html` now generates a `.gitignore` file in every workspace it produces, built from two tiers: a universal base (OS/editor cruft, `.env*`, `CLAUDE.local.md`, `*.log`) plus a per-type `localOnly` flag on specific folder checkboxes (e.g. `dados`/`data`, `outputs`, `models`, `logs`, `builds`, raw footage). Local-only folders get `folder/*` + `!folder/.gitkeep`, so the folder exists on a fresh clone but its contents never get committed. The checkbox label for any local-only folder is tagged in the UI (`· local only (.gitignore)` / `· só local (.gitignore)`) so the choice is visible before generating.
- **Reason:** direct implementation of the Collaboration and Security & privacy pillars — heavy or sensitive folder contents (raw datasets, trained models, logs, build artifacts) shouldn't ship to every collaborator via git, but the folder skeleton should still exist so the project structure is consistent for whoever clones it.
- **Also folded into this same push:** while implementing this, a separate parallel work session had already added 6 new project types directly to `src/workspace-kit.html` — `mobile`, `extension`, `hardware`, `course`, `marketing`, `podcast` — each with its own folders, defaults, stack/limits placeholders, and anchor file, following the same pattern as the original 11. These were merged in rather than redone. The project now ships **17 project types**, not 11 — the "v2 — 11 project types" decision above is superseded by this count; anywhere still saying "11 project types" (README, PROJECT.md status line) is stale and should be updated to match.
- **Alternatives considered:** gitignoring by folder name globally regardless of project type — discarded because the same folder name (e.g. "assets") is sensitive/heavy in one project type and fine to version in another; making every generated folder local-only by default — discarded, most generated folders (docs, src, notes) are exactly what should be versioned.

## 2026-07-21 — Multi-surface compatibility strategy + context-manager repositioning
- **Decision:** going forward, workspace//kit ships across three compatible surfaces: a **CLI** generator; a more robust **local Web App** that generates *and* manages workspaces (how much of that management also belongs in the CLI is still open); and the current **standalone HTML artifact**, kept as-is for as long as it stays viable as a Claude/browser artifact, or until a fuller project site replaces it. This is not "pick one" — all three are meant to coexist.
- **Feature rollout policy:** new features are built for all three surfaces wherever technically possible. Anything that needs git operations, spinning up a local process (e.g. Docker), or persistent managed state is CLI/Web-App-only by nature — a standalone HTML artifact can't touch git or the filesystem beyond a single browser-triggered download. Pure content-generation features (new files, new form fields, new generated text) stay available on all three, HTML included.
- **Decision:** the product's identity is evolving from a one-shot generator into a **project context manager** — useful across a project's whole lifecycle (ongoing decisions/tasks/changelog upkeep), not just at kickoff.
- **Decision:** the CHANGELOG.md + ADR-style DECISIONS.md rotation pattern (see the "Context.md file size" findings in the 2026-07-21 planning review: an on-demand/grep-only CHANGELOG.md with a ~3-month pruning window, and migrating DECISIONS.md entries past ~15 into individual files under `decisions/` with an index) is adopted for **both**: (a) this repository's own docs, and (b) as a future product convention the generator itself should offer, once workspace//kit becomes a context manager rather than just a generator. Neither is implemented yet — tracked in TASKS.md.
- **Supersedes (partially):** the "v2 — 100% client-side generation" decision (100% browser-side, no backend) now applies specifically to the **standalone HTML surface**, not the whole project — the CLI and Web App are expected to need their own runtime (a local process for the CLI, a local server for the Web App) to do things the HTML artifact structurally cannot.
- **Open tension, not resolved here:** a separate past session floated framing workspace-kit as strictly "Phase 1" (guided initial setup only, with any execution/handoff work explicitly out of scope). That framing may be in tension with the context-manager repositioning above, which implies an ongoing role beyond initial setup. Not resolved as part of this decision — flagged in TASKS.md for explicit follow-up rather than assumed either way.
- **Reason:** came out of a full project review (2026-07-21) — TASKS.md backlog, other Cowork session history, and open GitHub issues were all cross-checked in one pass; the owner confirmed this direction should absorb prior planning rather than replace it, and anything not aligned with it should be discontinued instead.

## 2026-07-21 — Shared generation engine across CLI/Web App/HTML
- **Decision:** the CLI, Local Web App, and standalone HTML artifact share the same generation logic — centralized/standardized, not three independent copies of the templates. This resolves the "blocking" open question left in `docs/specs/cli-generator.md` and `docs/specs/local-web-app.md`.
- **Reason:** the owner wants Templates (see `docs/specs/templates-feature.md`, issue #32) to work as shareable template files across surfaces — if each surface generated from its own copy of the logic, a template built on one surface wouldn't behave the same way generated from another, defeating the point of a portable template format.
- **Implication:** the built-in 17 project types are themselves candidates for eventually running through the same engine as user-defined templates (effectively "system templates"), rather than being special-cased — not decided yet, but worth keeping in mind so the engine isn't built in a way that special-cases the built-ins out of reach of the template system.
- **Open engineering follow-up (not resolved here):** the standalone HTML artifact has a hard "no build step" constraint (see CONTEXT.md), while a shared module is the natural shape for Node-based CLI/Web App code. The generation logic is data + string templating, not something that inherently needs a bundler, so a plain JS module includable both via `<script>` and via Node `require`/`import` is plausible — but the exact approach (single vanilla-JS file, small custom loader, etc.) still needs a concrete technical decision before implementation starts.
- **Applies to:** `docs/specs/cli-generator.md` (#20), `docs/specs/local-web-app.md` (#29), `docs/specs/templates-feature.md` (#32) — all three updated to reflect this.

## 2026-07-22 — Shared generation module seeded standalone, HTML artifact deferred
- **Decision:** `core/generator.js` was created as the shared generation engine mandated by the "2026-07-21 — Shared generation engine" decision above — plain Node-compatible JS (UMD-lite: `module.exports` for Node, `window.WorkspaceKitCore` for `<script>`), zero dependencies, no build step. It is a **copy-derived seed** of the pure data/generation logic already in `src/workspace-kit.html`'s `<script>` (the 17-type `TYPE_CONFIG`, `.gitignore`/agent-file/starter-prompt builders), with DOM reads (`els.*`, global `LANG`) replaced by explicit function parameters — same behavior, verified against fixture cases (`core/fixtures.json` + `core/check-fixtures.js`). `src/workspace-kit.html` itself is **not modified** and is **not wired to this module** — it keeps its own separate inline copy of the same logic.
- **Reason:** the natural approach (`workspace-kit.html` loading the module via `<script src="...">`) was proposed and explicitly rejected by the owner: it would break using `workspace-kit.html` as a **standalone artifact pasted directly into Claude.ai**, which has no relative-path filesystem access to load a sibling file (see CONTEXT.md — the HTML surface must stay self-contained inside Claude.ai/the browser). The owner's call: preserve that use case as-is; let the shared module exist purely for the CLI (and later Web App) to consume from day one. Going forward, generation-logic improvements get manually ported into the HTML's inline copy when it's easy to do so; otherwise they stay app-only (CLI/Web App), diverging from the artifact by design rather than by accident.
- **Alternatives considered:** `<script src="core/generator.js">` in the HTML — discarded, breaks the Claude.ai-pasted-artifact use case; a small Node/string-concat build step producing a bundled standalone HTML with the module inlined — discarded for now as more machinery than justified by today's need, revisit if manual-backport drift between the two copies becomes painful in practice.
- **Resolves:** the open engineering question left in the "2026-07-21 — Shared generation engine" decision and in `docs/specs/cli-generator.md`'s Open Questions ("exact technical shape of a module includable both via `<script>` and via Node `require`/`import`").

## 2026-07-26 — Product positioning sharpened; model-agnostic clarified; "project type" renamed to "kit"
- **Decision:** workspace//kit is positioned explicitly as a **workspace management and versioning tool** — for instructions, prose, and documentation — and explicitly **not** a code-versioning tool (git already does that; workspace//kit's planned Git integration is a user-friendly layer on top, not a replacement). **Model- and tool-agnostic** is now an explicit product principle, not just an implementation detail of the standalone HTML artifact.
- **Reason:** came out of a 2026-07-26 voice-note brainstorming session ("Notas de Áudio 26/07"), reviewed in this same session against the existing repo state before being logged.
- **Clarification (owner, 2026-07-26):** the note's line "the model can make commits and PRs" does **not** mean workspace//kit itself calls or hosts an AI model. It refers to whatever agent (Claude Code, Cursor, etc.) is already working inside a generated workspace — that agent commits/opens PRs, the user reviews and merges externally. Workspace//kit's own job is to track file state and prepare git-aware flows/instructions for that agent. This keeps the product consistent with the model-agnostic principle above and with CONTEXT.md's "no backend, no external API calls requiring a key" constraint. See TASKS.md, "Git as the integration layer."
- **Decision:** the built-in "project type" concept (17 folder/anchor-file presets) is renamed **"kit"** — built-ins become **"system kits"** — rather than "template," which was the other candidate name. **Reason:** "template" would collide with the already-planned, separately-sourced Templates feature (user-authored reusable structures, docs/specs/templates-feature.md, #32); "kit" avoids the collision and reinforces the product's own name, workspace//**kit**.
- **Timing:** decided to execute the rename now, before the CLI (#20) exposes "project type" in its public flag/prompt surface — renaming after that ships would be a breaking change to a public interface instead of an internal one.
- **Alternatives considered:** "template" for the rename — discarded for the naming collision above; renaming later alongside the Templates feature build — discarded, the CLI is the more time-sensitive constraint.
- **Not resolved here:** how the separate "Markdown Orchestrator" project gets folded into workspace//kit (port existing code vs. reimplement fresh) — flagged as open in TASKS.md, owner's call, not blocking anything else in this entry.
- **Also executed in this same session:** DECISIONS.md itself had passed the ~15-entry rotation trigger recorded in docs/specs/context-manager-conventions.md (#34) — see the "Archived — v1/v2 foundational decisions" section and "ADR-style rotation policy" note at the top of this file for the first execution of that policy (2026-07-26).

## 2026-07-28 — Local Web App gets its own stack and visual identity (React/Tailwind/shadcn), scoped per surface
- **Decision:** the Local Web App (#29) is built with **React + Tailwind + shadcn/ui**, with a build step. This is the explicit decision AGENTS.md's "don't add a build framework without an explicit decision" limit asks for — and it is **scoped to that surface only**. The standalone HTML artifact (`src/workspace-kit.html`) keeps its hard "single file, no build step, no framework" constraint unchanged, and `core/generator.js`/`core/inspect.js` keep their zero-dependency, no-build convention so both the CLI and the Web App can consume them. The limit in AGENTS.md is therefore now per-surface, not project-wide.
- **Reason:** a high-fidelity Claude Design prototype ("Workspace Kit Dashboard," 2026-07-27/28) was built on shadcn/ui and covers all five 2026-07-26 lifecycle features as one screen. Rebuilding that in framework-free HTML/CSS/JS would discard working markup and make the dark/light theming — which `DESIGN.md` treats as equally first-class, not a bolt-on — substantially harder for no benefit the artifact's constraint was protecting: that constraint exists so the artifact can be pasted into Claude.ai as a self-contained file, which has never applied to a locally-served app.
- **Decision:** the Web App's visual identity is the prototype's direction — neutral shadcn token base, Inter for UI text, JetBrains Mono for paths/metrics, one accent (amber/teal), status semantics fixed as green/amber/red plus a muted neutral, always color + icon + label together. This is logged rather than assumed, per CONTEXT.md's rule that brand changes are recorded, not made silently. It deliberately **does not** override `decisions/008-v2-visual-identity.md`: the artifact's terminal identity stands, and the two surfaces are allowed to read as related-but-distinct products (one-shot artifact vs. ongoing management app).
- **Alternatives considered:** reimplementing the prototype's look framework-free to preserve a single project-wide constraint — discarded, see Reason; deferring the stack choice to implementation time — discarded, it determines whether the prototype's code is reusable at all, so leaving it open would have made the prototype decorative rather than a head start.
- **Also in this pass:** `docs/specs/web-app-dashboard.md` written as the bridge spec between the prototype and the five lifecycle specs (#77–#81) — it owns rendering only, never domain logic; `docs/specs/local-web-app.md`'s "Design-system-level polish" Non-Goal retired as obsolete; the prototype's markup versioned at `docs/design/workspace-kit-dashboard.dc.html` (the full Claude Design export, including its ~650KB bundle, deliberately not committed).

## 2026-07-29 — Issue tracker pruned to the spec convention; spec→issue sync keyed instead of title-matched
- **Decision:** the GitHub issue tracker is brought back to this repo's stated convention — **one curated parent issue per spec, with its Must-Have (P0) requirements as linked sub-issues** — by closing everything that predates or duplicates it. 78 issues closed in one pass, 168 open → 90: the 41 raw TASKS.md-bullet issues from the 2026-07-26 automation flood (#36–#76), 30 auto-titled twins of the hand-curated sub-issues #82–#111, 5 legacy issues whose work is provably done (#3, #10, #11, #18, #19), and 2 duplicates created the same day by the rename (#166, #168). Every closure carries a comment naming the canonical issue or the commit that completed it — nothing is closed silently.
- **Reason:** the tracker had drifted into three overlapping layers (pre-spec bullets, curated sub-issues, and auto-generated twins of those same sub-issues), so it no longer answered "what is actually left to do." The owner asked for a clean slate before changing the project's direction.
- **Decision:** the `Sync specs to Issues` workflow matches issues by a **stable sync key** (`<!-- sync-key: <spec>#p0-<n> -->` in the issue body), not by exact title. Retired (struck-through) requirement bullets are skipped. Titles are never rewritten unless explicitly asked for.
- **Reason:** title matching failed twice for real on this date. The kit rename reworded a P0 bullet and duplicated #126 as #166; a bullet that had just been struck through and retired became #168, titled with the literal `~~...~~` markup. Both failures are structural, not accidents — any future rewording would have repeated them. Ordinals span all bullets including retired ones, so retiring a requirement does not renumber the rest and invalidate their keys.
- **Also decided:** when adopting pre-key issues, the parent's **existing linked sub-issue at the same ordinal wins over an exact-title match**. This is what keeps the hand-curated #82–#111 canonical rather than letting the auto-titled twins take their place. Known limitation, documented in the script: keys are positional, so *reordering* P0 bullets within a spec will mismatch issues — adding and retiring are safe.
- **Alternatives considered:** requiring an explicit stable id in every spec bullet (e.g. `- (P0-3) …`) — discarded as noise in a document meant to be read by humans; hashing the bullet text as the key — discarded, it is the text that changes, which is the whole problem.
- **Implementation note:** the logic moved out of an inline heredoc in the workflow YAML into `.github/scripts/sync_specs_to_issues.py`, which takes `--dry-run`. Every number above was verified against the live repo with that flag before anything was written.
