## 2026-07-22 — Resolved: workspace//kit is not limited to "Phase 1" (initial setup only)
- **Decision:** the informal "Phase 1" framing floated in a separate past session — guided initial setup only, with any execution/handoff work explicitly out of scope — is retired. workspace//kit's scope now explicitly includes an ongoing role across a project's whole lifecycle, per the 2026-07-21 context-manager repositioning: not just producing the initial file set, but supporting ongoing decisions/tasks/changelog upkeep, and — where a surface technically allows it (CLI/Web App) — execution-adjacent capabilities like git operations, Docker environment spin-up, and persistent workspace management (see docs/specs/local-web-app.md #29, docs/specs/docker-environment-generation.md #33).
- **Reason:** explicit owner call (2026-07-22) — the project's scope has expanded, and the context-manager repositioning should take precedence over the earlier, narrower framing rather than coexist with it.
- **Alternatives considered:** keep both framings and scope each surface individually (e.g., HTML = Phase 1 only, CLI/Web App = full lifecycle) — discarded; the owner's direction is that the constraint itself should be removed project-wide, not partitioned by surface.
- **Implication:** `docs/PRD.md` (this repo's own self-generated anchor file, produced by an earlier version of the generator) still listed "Persistence across sessions," "Editing templates through the UI," and parts of "Direct integration to create the workspace remotely" under "Out of scope (for now)" — all now explicitly in scope per the CLI/Web App/Templates specs. Updated in this same pass so it stops contradicting the current direction.
- **Resolves:** the "Open tension, not resolved here" bullet in the "2026-07-21 — Multi-surface compatibility strategy + context-manager repositioning" decision above, and the corresponding TASKS.md follow-up item.

## 2026-07-26 — Product positioning sharpened; model-agnostic clarified; "project type" renamed to "kit"
- **Decision:** workspace//kit is positioned explicitly as a **workspace management and versioning tool** — for instructions, prose, and documentation — and explicitly **not** a code-versioning tool (git already does that; workspace//kit's planned Git integration is a user-friendly layer on top, not a replacement). **Model- and tool-agnostic** is now an explicit product principle, not just an implementation detail of the standalone HTML artifact.
- **Reason:** came out of a 2026-07-26 voice-note brainstorming session ("Notas de Áudio 26/07"), reviewed in this same session against the existing repo state before being logged.
- **Clarification (owner, 2026-07-26):** the note's line "the model can make commits and PRs" does **not** mean workspace//kit itself calls or hosts an AI model. It refers to whatever agent (Claude Code, Cursor, etc.) is already working inside a generated workspace — that agent commits/opens PRs, the user reviews and merges externally. Workspace//kit's own job is to track file state and prepare git-aware flows/instructions for that agent. This keeps the product consistent with the model-agnostic principle above and with CONTEXT.md's "no backend, no external API calls requiring a key" constraint. See TASKS.md, "Git as the integration layer."
- **Decision:** the built-in "project type" concept (17 folder/anchor-file presets) is renamed **"kit"** — built-ins become **"system kits"** — rather than "template," which was the other candidate name. **Reason:** "template" would collide with the already-planned, separately-sourced Templates feature (user-authored reusable structures, docs/specs/templates-feature.md, #32); "kit" avoids the collision and reinforces the product's own name, workspace//**kit**.
- **Timing:** decided to execute the rename now, before the CLI (#20) exposes "project type" in its public flag/prompt surface — renaming after that ships would be a breaking change to a public interface instead of an internal one.
- **Alternatives considered:** "template" for the rename — discarded for the naming collision above; renaming later alongside the Templates feature build — discarded, the CLI is the more time-sensitive constraint.
- **Not resolved here:** how the separate "Markdown Orchestrator" project gets folded into workspace//kit (port existing code vs. reimplement fresh) — flagged as open in TASKS.md, owner's call, not blocking anything else in this entry.
- **Also executed in this same session:** DECISIONS.md itself had passed the ~15-entry rotation trigger recorded in docs/specs/context-manager-conventions.md (#34) — see the "Archived — v1/v2 foundational decisions" section and "ADR-style rotation policy" note at the top of this file for the first execution of that policy (2026-07-26).

## 2026-07-28 — Local Web App gets its own stack and visual identity (React/Tailwind/shadcn), scoped per surface
- **Decision:** the Local Web App (#29) is built with **React + Tailwind + shadcn/ui**, with a build step. This is the explicit decision AGENTS.md's "don't add a build framework without an explicit decision" limit asks for — and it is **scoped to that surface only**. The standalone HTML artifact (`src/workspace-kit.html`) keeps its hard "single file, no build step, no framework" constraint unchanged, and `core/generator.js`/`core/inspect.js` keep their zero-dependency, no-build convention so both the CLI and the Web App can consume them. The limit in AGENTS.md is therefore now per-surface, not project-wide.
- **Reason:** a high-fidelity Claude Design prototype ("Workspace Kit Dashboard," 2026-07-27/28) was built on shadcn/ui and covers all five 2026-07-26 lifecycle features as one screen. Rebuilding that in framework-free HTML/CSS/JS would discard working markup and make the dark/light theming — which `DESIGN.md` treats as equally first-class, not a bolt-on — substantially harder for no benefit the artifact's constraint was protecting: that constraint exists so the artifact can be pasted into Claude.ai as a self-contained file, which has never applied to a locally-served app.
- **Decision:** the Web App's visual identity is the prototype's direction — neutral shadcn token base, Inter for UI text, JetBrains Mono for paths/metrics, one accent (amber/teal), status semantics fixed as green/amber/red plus a muted neutral, always color + icon + label together. This is logged rather than assumed, per CONTEXT.md's rule that brand changes are recorded, not made silently. It deliberately **does not** override `decisions/008-v2-visual-identity.md`: the artifact's terminal identity stands, and the two surfaces are allowed to read as related-but-distinct products (one-shot artifact vs. ongoing management app).
- **Alternatives considered:** reimplementing the prototype's look framework-free to preserve a single project-wide constraint — discarded, see Reason; deferring the stack choice to implementation time — discarded, it determines whether the prototype's code is reusable at all, so leaving it open would have made the prototype decorative rather than a head start.
- **Also in this pass:** `docs/specs/web-app-dashboard.md` written as the bridge spec between the prototype and the five lifecycle specs (#77–#81) — it owns rendering only, never domain logic; `docs/specs/local-web-app.md`'s "Design-system-level polish" Non-Goal retired as obsolete; the prototype's markup versioned at `docs/design/workspace-kit-dashboard.dc.html` (the full Claude Design export, including its ~650KB bundle, deliberately not committed).

## 2026-07-29 — "project type" → "kit" rename executed; generated text deliberately excluded
- **Decision:** the rename decided 2026-07-26 is executed. Workspace//kit's own surface now says **kit** everywhere: `KIT_CONFIG` (both copies of the generation logic), `applyKitDefaults`/`populateKitSelect`, the DOM ids `pkit`/`pkitLabel`, the form label "Kit" in both EN and PT, the `kit` input key on `core/generator.js`'s `generate`/`buildFileMap`/`buildStarterPrompt` API, `core/fixtures.json` inputs, `core/parity-check.js`, `research/kits/` (renamed from `research/project-types/`), and README/CONTEXT/specs wording.
- **Decision (scope boundary, new here):** the text workspace//kit **generates** is *not* renamed — a generated `PROJECT.md` still has a `## Project type` heading and the starter prompt still says `Project type:` / `Tipo de projeto:`. **Reason:** the 2026-07-26 rationale was (a) avoiding a collision with the user-authored Templates feature (#32) and (b) not shipping "project type" as a public CLI flag (#20). Neither reaches inside a generated workspace. That text is read by people and agents who have never heard of workspace//kit, for whom "project type" is self-explanatory and "kit" is unexplained product jargon — leaking the product's internal vocabulary into every user's files would cost clarity for no stated benefit.
- **Consequence, used as the test:** because generated output is unchanged, `core/fixtures.json`'s recorded `expected` blocks were left untouched and `npm run test:fixtures` + `npm run test:parity` both still pass. A rename that changed any generated workspace would have failed them. This is the evidence the refactor is behavior-preserving, not just a claim.
- **Alternatives considered:** renaming the generated headings too, for one consistent vocabulary end-to-end — discarded per the reasoning above, but cheap to reverse: it is two string pairs in each copy of the generation logic plus re-recording the fixtures. Flagged in TASKS.md as the owner's to overrule.
- **Timing:** deliberately before the CLI (#20) ships, per the 2026-07-26 entry — after that, `--type` would be a public interface and the rename a breaking change.
- **Process note:** CLAUDE.md asks for plan mode or an equivalent review step before structural changes to `src/workspace-kit.html`. This landed as a reviewable draft PR instead of an unattended push to `main`, with the parity suite as the mechanical check — the rename touches identifiers and two UI strings, not the file's structure.
- **Also in this pass:** `index.html` (the GitHub Pages copy of the artifact) had silently fallen a version behind — it never received the PT starter-prompt fix from 2026-07-27. Re-mirrored from `src/workspace-kit.html`. Worth a convention: that copy is a build output and should be re-mirrored in the same commit that touches the artifact, otherwise the published page drifts unnoticed.

## 2026-07-29 — Issue tracker pruned to the spec convention; spec→issue sync keyed instead of title-matched
- **Decision:** the GitHub issue tracker is brought back to this repo's stated convention — **one curated parent issue per spec, with its Must-Have (P0) requirements as linked sub-issues** — by closing everything that predates or duplicates it. 78 issues closed in one pass, 168 open → 90: the 41 raw TASKS.md-bullet issues from the 2026-07-26 automation flood (#36–#76), 30 auto-titled twins of the hand-curated sub-issues #82–#111, 5 legacy issues whose work is provably done (#3, #10, #11, #18, #19), and 2 duplicates created the same day by the rename (#166, #168). Every closure carries a comment naming the canonical issue or the commit that completed it — nothing is closed silently.
- **Reason:** the tracker had drifted into three overlapping layers (pre-spec bullets, curated sub-issues, and auto-generated twins of those same sub-issues), so it no longer answered "what is actually left to do." The owner asked for a clean slate before changing the project's direction.
- **Decision:** the `Sync specs to Issues` workflow matches issues by a **stable sync key** (`<!-- sync-key: <spec>#p0-<n> -->` in the issue body), not by exact title. Retired (struck-through) requirement bullets are skipped. Titles are never rewritten unless explicitly asked for.
- **Reason:** title matching failed twice for real on this date. The kit rename reworded a P0 bullet and duplicated #126 as #166; a bullet that had just been struck through and retired became #168, titled with the literal `~~...~~` markup. Both failures are structural, not accidents — any future rewording would have repeated them. Ordinals span all bullets including retired ones, so retiring a requirement does not renumber the rest and invalidate their keys.
- **Also decided:** when adopting pre-key issues, the parent's **existing linked sub-issue at the same ordinal wins over an exact-title match**. This is what keeps the hand-curated #82–#111 canonical rather than letting the auto-titled twins take their place. Known limitation, documented in the script: keys are positional, so *reordering* P0 bullets within a spec will mismatch issues — adding and retiring are safe.
- **Alternatives considered:** requiring an explicit stable id in every spec bullet (e.g. `- (P0-3) …`) — discarded as noise in a document meant to be read by humans; hashing the bullet text as the key — discarded, it is the text that changes, which is the whole problem.
- **Implementation note:** the logic moved out of an inline heredoc in the workflow YAML into `.github/scripts/sync_specs_to_issues.py`, which takes `--dry-run`. Every number above was verified against the live repo with that flag before anything was written.

## 2026-07-29 — `core/inspect.js` implemented; the inspection layer's open questions closed
- **Decision:** the workspace inspection layer (docs/specs/workspace-inspection-layer.md → #77) is implemented as `core/inspect.js`, the read-side counterpart to `core/generator.js` — same conventions (plain Node-compatible JS, zero runtime dependencies, no build step), verified by `npm run test:inspect`, whose 18 cases map 1:1 onto the spec's P0 acceptance criteria so a failure names the requirement it breaks.
- **Decision (was an Open Question):** estimated token counts use the **characters ÷ 4 heuristic**, swappable through an `estimateTokens` option. A real tokenizer would mean a runtime dependency, which is exactly the convention this module exists to mirror; and #78's own P0 already assumed chars ÷ 4, so picking anything else would have split the two. Consumers must present the number as an estimate (#169 P0 requires it).
- **Decision (was an Open Question):** one **instruction unit = one markdown heading section**, plus a preamble unit for content before the first heading — a generated `CLAUDE.md` opens with a bare `@AGENTS.md` import, which is itself an instruction and would otherwise be invisible. IDs are `path#heading-slug`, deterministic from content, deduplicated with a numeric suffix. The Markdown Orchestrator still owns the definitive unit; when it lands, `parseInstructions` is the single place that changes.
- **Decision (was an Open Question):** **Node-only export.** No `window.*` global like `core/generator.js`'s UMD-lite wrapper, since reading an arbitrary folder needs `fs` and no browser surface consumes this.
- **Decision (not in the spec, forced by reality):** the scan **honours the workspace's own `.gitignore`** and **skips nested git repositories**. Inspecting this repo without either produced 693 files, 14.6 MB and 7.7 seconds — it was indexing `.claude_global/` and a `.claude/worktrees/` checkout of the repo itself, and 9 of the 10 "broken cross-references" it reported came from third-party plugin content. With both rules: 72 files, 320 ms, zero broken references. Health-check verdicts computed over the first set would have been meaningless, so this is a correctness matter, not an optimisation. Opt out with `respectGitignore: false`. A directory carrying its own `.git` is treated as a separate project rather than part of this workspace.
- **Decision:** **markdown links inside inline code do not create graph edges** (prose mentions still do). The spec's own line 43 writes "standard `[text](path)` links" as a syntax example, and the first implementation dutifully recorded an edge to a file named `path` — a fabricated edge, which the P0 acceptance criterion explicitly forbids. Mentions are deliberately exempt: they only ever resolve against files that exist, so they cannot invent a target, and this repo's prose refers to real files in backticks constantly.
- **Consequence worth keeping in view:** the fixture workspace the tests run against is **generated by `core/generator.js` at test time** rather than committed as static files, so the read side is always checked against what the write side currently produces. A generation change the inspector cannot read fails the suite instead of reaching a consumer.
- **Alternatives considered:** committing a static fixture workspace — discarded, it would drift from the generator exactly like the HTML artifact's inline copy already does; reporting unresolved edges only when the target looks like a filename — discarded as a second mechanism for a bug the inline-code rule already fixes at its cause.

## 2026-07-29 — Local Web App reaches the filesystem through a local Node server
- **Decision:** the Local Web App (#29) talks to the filesystem via a **local Node server**, not the browser's File System Access API. Confirmed by the owner 2026-07-29, closing the question left open in both docs/specs/local-web-app.md (→ #29) and docs/specs/web-app-dashboard.md (→ #169).
- **Reason:** `core/inspect.js` uses Node's `fs`, and every module built on it (`core/doctor.js`, the planned `core/git.js`) inherits that. The File System Access API could not execute any of them — choosing it would have meant rewriting `core/` against an abstract file backend and giving up the property that the CLI and the Web App run literally the same code. Git operations (#79) settle it independently: a browser cannot drive git at all.
- **Consequence:** the dashboard is a client of a small local HTTP surface over `core/`, not a reimplementation of it. Anything the Web App can compute, the CLI can too, by construction.

## 2026-07-29 — Workspace health check implemented; the doctor judges, the inspector reports
- **Decision:** docs/specs/workspace-health-check.md (→ #78) is implemented as `core/doctor.js` plus a `workspace-kit doctor` command in `bin/workspace-kit.js`. `diagnose()` takes an **inspection index, not a folder path** — it never walks the filesystem itself. That keeps `core/inspect.js` the single module in this codebase that touches the disk, and makes the boundary enforceable rather than aspirational (a test asserts `doctor.js` never requires `fs`).
- **Decision (was an Open Question):** threshold **banding** around #34's ~300-line anchor is *warning at 90% of the limit, over-budget past it*. That satisfies #78's own acceptance criterion (250 healthy / 300 warning / 400 over-budget) and leaves one knob (`warnRatio`) to retune instead of three separate numbers. Thresholds are overridable per call and via `--max-lines`, per the spec's P1.
- **Decision (was an Open Question):** **stale-instruction detection is scoped to the mechanically-detectable case** — an instruction section containing a reference to a file that does not exist. #78's own Open Questions propose exactly this for v1; judging an instruction "obsolete but still linked" needs real usage data, so it is not guessed at.
- **Decision:** skills (`.claude/skills/**`) are **excluded from the always-loaded budget**. A SKILL.md is read when the skill is invoked, not at session start, so counting it would inflate the very figure the budget exists to protect.
- **Found by dogfooding:** the first run against this repo returned verdict `needs-attention` alongside the line "No suggestions — this workspace is within every threshold", because a *warning*-level finding produced no suggestion. A warning with nothing to do about it is noise. Warnings now carry their own low-severity suggestion, and the all-clear line is only printed when the verdict actually is healthy. Regression test: `P0-5e`.
- **Alternatives considered:** having the doctor read files itself for convenience — discarded, it would create the second workspace parser #77 exists to prevent; hardcoding the banding rather than deriving it from a ratio — discarded, the anchor is fixed by #34 but the banding is explicitly the owner's to retune.

## 2026-07-29 — Reading `queue/` and `SESSIONS.md` belongs to the inspection layer
- **Decision:** `core/inspect.js` gains `parseQueueItem()` and `parseSessions()`, exposing `index.queue` and `index.sessions`. Neither #80 nor #81 grows its own parser.
- **Reason:** cross-referencing the Claude Design prototype's 238 `{{ }}` placeholders against the specs exposed an ownership hole. Both docs/specs/document-ingestion-queue.md (→ #80) and docs/specs/cross-tool-session-log.md (→ #81) explicitly defer *reading* their own files to the inspection layer — "the kind of thing the Workspace inspection layer exists to eventually provide" — but #77's Non-Goals stopped at files, instructions and the graph, so nobody owned it. The dashboard (#169) needs both, and leaving it unowned is exactly the five-slightly-different-parsers outcome #77 exists to prevent.
- **Decision:** queue status is **normalised** to `pending`/`ingested` while the raw string is kept, and a test asserts the parser agrees with the documented `grep -l "Status: Pending" queue/*.md` convention. Two ways of answering "is this ingested" that can disagree would be worse than one.
- **Scope note:** this is the *read* half only. Both specs' generation half — emitting `SESSIONS.md`, the standing "every session" instruction, and the `queue/` stub convention into generated workspaces on all three surfaces — is still open. This repo dogfoods both conventions already, but `core/generator.js` does not yet produce them.

## 2026-07-29 — Git layer: the unblocked half built, the PR/worktree half deliberately not
- **Decision:** `core/git.js` implements the part of docs/specs/git-integration-layer.md (→ #79) that no open question gates — file-state tracking, the safe-edit substrate, the plain-language change summary, and the templated commit message — plus a `workspace-kit status` command. The **PR flow and worktree management are not built**, because each is gated on a "(Product — Alexandre)" question in the spec: hosting-provider scope (GitHub-only via `gh` vs. provider-agnostic) and worktree placement/naming (auto-placed by convention vs. prompted). Both answers determine the implementation, so building ahead of them means throwing a version away.
- **Decision:** when a file is staged *and* has further unstaged edits, it reports as `modified-unstaged`. The unrecorded change is the one a caller about to overwrite the file needs to know about; reporting `staged` there would make the safe-edit check quietly wrong in exactly the case it exists for.
- **Decision:** git is driven by `execFileSync` with explicit argument arrays, never a shell string. A test writes a file named `a file; echo pwned > owned.txt.md` and asserts it is reported literally and nothing executes.
- **Reason for the guardrail tests:** #79's model-agnostic requirement and its "the HTML artifact is unchanged" requirement are both product rules that are easy to violate later by accident. Each is now a test — one asserting `core/git.js` contains no outbound call and depends only on `child_process`/`path`, another asserting `src/workspace-kit.html` never references this feature.

## 2026-07-29 — The local server is zero-dependency and read-only
- **Decision:** `core/server.js` — the local HTTP surface the Web App dashboard consumes — uses Node's own `http` and takes **no dependencies**. The React/Tailwind/shadcn build step decided 2026-07-28 is scoped to the *front end that consumes* this server, not to the server itself. Putting a framework here would place a dependency underneath every `core/` consumer, including the CLI.
- **Decision:** it owns **no domain logic**. Every endpoint is a thin envelope over `inspect`/`doctor`/`git`. That is what makes the CLI and the Web App produce identical answers by construction rather than by discipline — the property that motivated choosing a local server over the browser File System Access API in the first place.
- **Decision:** the server is **read-only** — every non-GET method is refused, and it must not grow write endpoints ahead of #79's blocked commit/PR/worktree questions. `/api/dashboard` reports `capabilities: {commit: false, pullRequest: false, worktrees: false}` so the UI renders those controls as unavailable instead of drawing live-looking buttons over nothing.
- **Decision:** `/api/dashboard` returns all five sections from **one scan**. Letting the dashboard issue four requests would let its sections disagree with each other mid-refresh, which is a worse failure than a slightly larger payload.
- **Security posture:** binds to `127.0.0.1` only and refuses any workspace path resolving outside the root it was started with. A browser page on another origin can still reach localhost, so "read any path on disk" would be a real hole, not a theoretical one.

## 2026-07-29 — Git layer scoped to local git; push and PRs deferred as their own step
- **Decision:** the git integration layer (`docs/specs/git-integration-layer.md` → #79) is **local-only** for now. It tracks state, drives commits and manages worktrees against the local repository, and contacts no remote — nothing is pushed, no PR is opened, no hosting provider is contacted. This closes the spec's "hosting-provider scope for the PR flow" open question by removing it from scope rather than answering it: the question stands, but it is not this step's to answer.
- **Reason:** the owner's call. Remote operations drag in authentication and a hosting-provider surface whose security deserves a deliberate pass of its own, and none of the local value — safe edits, parallel agents, plain-language commits — depends on them. Shipping the local half now is strictly better than a half-built remote half alongside it.
- **Alternatives considered:** building a GitHub-only PR flow via `gh` now and generalising later — discarded, it front-loads the provider decision the owner explicitly wants to take later, and a `gh` dependency is hard to retract once flows depend on it; a provider-agnostic abstraction over push/PR with no provider implemented — discarded as machinery with nothing behind it.
- **Enforced, not just documented:** `npm run test:git` asserts `core/git.js` contains no push/fetch/clone/pull and no `gh pr` call, so "local only" fails the build if it stops being true.
- **Applies to:** `docs/specs/git-integration-layer.md` (#79), `core/git.js`, `bin/workspace-kit.js`.

## 2026-07-29 — Worktrees: convention by default, override always available
- **Decision:** worktree placement and naming follow a convention the user never has to think about — `<workspace>/.worktrees/<name>`, on a branch of the same name — while `--path` and `--branch` let the user override either. This answers the spec's "auto-place vs. prompt every time" question with *both*, ordered: convention first, control on request. Removal keeps the branch; deleting a branch is a separate, more destructive decision than removing a directory.
- **Reason:** the owner's call, and the two options were never really exclusive — prompting every time taxes the common case (spin up an isolated copy for another agent), while a rigid convention blocks the uncommon one. A default that is right most of the time plus an explicit escape hatch costs one extra flag and no ambiguity.
- **Why inside the workspace, not a sibling folder** (the spec's own example was `../workspace-name-agent2/`): a workspace stays one movable, self-contained directory, and every other module here already refuses to reason about paths outside the workspace root — `core/server.js` rejects them outright. Nesting is only safe because the read side already accounts for it: `core/inspect.js` skips nested git repositories, so a worktree's files never get folded into the parent's index or health check. A sibling would make a workspace's own worktrees the one thing living outside itself.
- **Consequence handled here:** any worktree placed inside the repository — by convention *or* by the user's `--path` — would otherwise show up in the parent's own status as a stray directory. Creating one adds the ignore rule, once, under a single heading. This is the same defect `workspace-kit status` found in this repo (`.claude/worktrees/` untracked), fixed at the source rather than by hand.
- **Alternatives considered:** sanitising invalid worktree names into valid ones — discarded, quietly rewriting a name the user chose creates the worktree somewhere other than where they asked, which is worse than refusing; deleting the branch on removal — discarded, it can hold the only copy of committed work.
- **Applies to:** `docs/specs/git-integration-layer.md` (#79), `core/git.js`, `bin/workspace-kit.js`.

## 2026-07-29 — Templates and the shared instruction library do not conflict: generation ends where management begins
- **Decision:** the shared instruction library (TASKS.md) is **not** blocked by the Templates spec's "no live link between a template and workspaces generated from it" Non-Goal. The two operate in different phases and the Non-Goal was read too broadly.
- **Reason:** the owner's correction, and it is right. A template is a **generation-time** artifact: a one-shot source that lays a workspace's foundation and is done. From the moment that folder exists it is a living workspace, and everything after that — including whether it keeps shared instructions in sync with a central library — is **management**, a different phase with a different owner. The Non-Goal constrains *templates* specifically: it rules out versioning templates and diffing template updates against already-generated workspaces. A library→workspace link established after generation is a different relationship between different objects, and nothing in that Non-Goal reaches it.
- **Wider point worth keeping:** generation and management are separate phases, and this codebase already splits exactly that way — `core/generator.js` writes, `core/inspect.js`/`doctor.js`/`git.js` manage. Blockers should be checked against which phase they actually constrain before being treated as binding.
- **Correcting the record:** the 2026-07-29 report and TASKS.md both listed this as blocked pending reconciliation. It was not blocked; the analysis conflated "reusable source of text" with "template". The shared instruction library now needs a spec, not a decision.
- **Applies to:** `docs/specs/templates-feature.md` (#32), TASKS.md.
