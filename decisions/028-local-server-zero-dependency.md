## 2026-07-29 — The local server is zero-dependency and read-only
- **Decision:** `core/server.js` — the local HTTP surface the Web App dashboard consumes — uses Node's own `http` and takes **no dependencies**. The React/Tailwind/shadcn build step decided 2026-07-28 is scoped to the *front end that consumes* this server, not to the server itself. Putting a framework here would place a dependency underneath every `core/` consumer, including the CLI.
- **Decision:** it owns **no domain logic**. Every endpoint is a thin envelope over `inspect`/`doctor`/`git`. That is what makes the CLI and the Web App produce identical answers by construction rather than by discipline — the property that motivated choosing a local server over the browser File System Access API in the first place.
- **Decision:** the server is **read-only** — every non-GET method is refused, and it must not grow write endpoints ahead of #79's blocked commit/PR/worktree questions. `/api/dashboard` reports `capabilities: {commit: false, pullRequest: false, worktrees: false}` so the UI renders those controls as unavailable instead of drawing live-looking buttons over nothing.
- **Decision:** `/api/dashboard` returns all five sections from **one scan**. Letting the dashboard issue four requests would let its sections disagree with each other mid-refresh, which is a worse failure than a slightly larger payload.
- **Security posture:** binds to `127.0.0.1` only and refuses any workspace path resolving outside the root it was started with. A browser page on another origin can still reach localhost, so "read any path on disk" would be a real hole, not a theoretical one.
